## 依赖关系的问题^[[1. Introduction - Nix Reference Manual](https://nixos.org/manual/nix/stable/introduction)]

管理软件包的依赖关系是包管理器的重要职责，同时也是最容易引发问题的部分。

### 依赖冲突

由依赖关系引起的种种问题，因其棘手程度而被俗称为**依赖地狱**（**Dependency Hell**）^[[Dependency hell - Wikipedia](https://en.wikipedia.org/wiki/Dependency_hell)]。这里我们只谈其中一种：**依赖冲突**。

设想这样一种状况。

应用 A 和应用 B 都依赖共享库 C，但 A 需要 C 的 1.0 版，B 需要 2.0 版。此时，如果共享库 C 的 1.0 版和 2.0 版之间不兼容，A 或 B 中的某一方行为就会发生变化，最糟的情况下甚至无法运行。让同一个软件包的不同版本共存本来就很困难，依赖关系的解析也会变得极其复杂。

此外，对共享库 C 的改动不仅会影响应用 A 和 B，还可能波及所有依赖它的软件包。

这可以说是软件包依赖关系中的共享可变状态所引发的问题。共享可变状态会让改动的影响范围难以预测，并导致各种冲突。不只是包管理器，在任何系统中这都是应当尽可能避免的状态。

### 隐式依赖

软件包的依赖关系，是由包管理器自动获取软件包定义中所记述的依赖包来解决的。然而，绝大多数包管理器都无法完整地追踪依赖关系。

你是否有过这样的经历：尝试构建某个软件包，却因为某个依赖包没有安装而失败？当软件包定义中的依赖声明有所遗漏，或者存在该包管理器所覆盖的生态之外的依赖时，包管理器就无法自动解决，只能由用户手动处理。

许多软件包都擅自假定目标环境中已经安装了某些特定的软件包。例如，除非是 Go 这类进行静态链接的语言，几乎所有程序都依赖 libc，但基本上没人会专门在软件包定义中把它写成依赖项。「请先安装 xxx」——这种一上手就要求用户手动解决依赖的软件也并不少见。

## 可复现性的难题

前述与依赖关系有关的问题，在现代这种庞大而复杂的软件包管理中会变得更加严重。因此，包管理器也在不断进化自身的功能，以回应日益复杂的软件开发需求。

然而，即便工具的功能越来越强，可复现性的问题依然没有被彻底解决。现代编程语言的包管理器在设计上做了不少避免陷入依赖地狱的努力，但大多数操作系统的包管理器并非如此设计。而隐式依赖的问题，目前也只能依靠开发者自己多加留意。

作为在包管理器之外解决这个问题的机制，Docker 出现了。Docker 乃至容器虚拟化技术为开发环境搭建、构建和部署带来了革新。它把从应用到中间件的一切整个打包进一个容器，从而大幅提升了可复现性。

但是，Docker 基本上是作为运行环境来使用的。虽然也有 [Flatpak](https://flatpak.org) 这类以容器管理并运行应用的技术，但把所有软件都虚拟化终究是不现实的。另外，Docker 在环境隔离方面确实出色，在可复现性方面却并不完备——因为即使使用 Docker，解析其内部运行软件的依赖关系的，仍然是传统类型的包管理器。

## Nix 这个解决方案

在这世上，能以最接近完美的形式解决上述问题的技术，正是 Nix。

1. 依赖冲突**在原理上**不会发生
2. **以机械化的方式**保证不存在隐式依赖

这绝不是魔法，其秘密就藏在构建系统之中。Nix 对软件包的构建施加了极为严格的约束。Nix 以严苛的戒律约束自身，从而正面迎战自依赖地狱而来的恶魔。

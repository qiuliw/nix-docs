我们来看看 Nix 的构建系统。

Nix 的构建系统是**纯函数式**的。这正是 Nix 被称为纯函数式包管理器的原因，也是实现「可复现性」的关键所在。

## 纯函数

大多数编程语言中的「函数」与数学上的「函数」是完全不同的概念。编程语言的函数准确来说并不是函数，而是所谓的**子程序**（或**过程**）。子程序指的是「一组处理的集合」。

而数学上的函数有明确的定义。抛开数学术语简单地说，「输入一旦确定，输出就唯一确定的那种关系」就叫作函数^[数学中的函数被定义为集合论中的**映射**。对集合 $A$ 的所有元素各自恰好对应到集合 $B$ 中一个元素的规则 $f$，称为「从集合 $A$ 到集合 $B$ 的映射 $f$」。]。下面是函数的示意图。

![函数的示意图。从左侧的输入集合到右侧的输出集合的映射用红色箭头表示。从输入集合的圆形元素各自伸出一支箭头，指向输出集合的菱形元素。](/images/nix-introduction/mapping.png)
_函数_

每个圆形元素都各自伸出一支箭头，指向一个菱形元素。

反过来，一个输入对应多个输出、即输入对输出是一对多的关系，就不是函数。

![并非函数的集合对应关系图解。从左侧的输入集合到右侧的输出集合的对应关系用红色箭头表示。](/images/nix-introduction/correspondence.png)
_不是函数_

在编程语言的语境中，为了把子程序和数学上的函数区分开来，人们特意把数学意义上的函数称为**纯函数**。而把函数当作纯函数（而非子程序）来处理的编程语言，则称为**纯函数式语言**。

### 纯函数的特性

#### 没有副作用^[[プログラム言語論 - 筑波大学](https://www.cs.tsukuba.ac.jp/~kam/lecture/plm2011/5-web.pdf)]

纯函数不具有**副作用**。函数的主作用是针对参数返回一个值。如果函数除了返回值之外还做了别的事情，那么这个函数就带有副作用。
具体来说，以下这些都属于副作用：

- 修改状态
- IO（文件操作、标准输入输出、访问互联网，等等……）
- 等等……

访问函数外部的、除参数之外的信息就相当于副作用。不过这些操作在使用计算机时都是必不可少的，所以纯函数式语言会设法让副作用也能以纯粹的方式来处理。

#### 引用透明性

**引用透明性**指的是对同样的参数总是返回同样的值这一性质。只要想想数学函数的定义，就会发现这是理所当然的性质。
如果某个函数会因执行的时机或环境不同而返回不同的结果，那它就不是引用透明的。

## 纯函数式构建系统

事实上，如果去思考理想的构建系统应当具备什么性质，会发现它恰好与纯函数的性质完全吻合。

首先，理想的构建应当是可复现的。
不可复现的构建，即使从同样的源代码构建，也会因环境或时机不同而导致构建产物的内容发生变化，最糟的情况甚至构建失败。

![非单射关系的图解。从左侧的圆形伸出三支红色箭头，分别指向右侧的菱形、长方形和圆形。](/images/nix-introduction/not-pure-build.png)
_没有可复现性的状态_

而在可复现的构建中，无论何时、在什么环境下都能得到相同的构建产物。理想的状态是：构建产物由源代码唯一确定，也就是说构建成为一个纯函数。

![单射关系的图解。从左侧的圆形伸出一支红色箭头，指向右侧的菱形。](/images/nix-introduction/pure-build.png)
_具有可复现性的状态_

让我们把软件包的构建看作一个函数。

$$
f(构建输入) = 构建产物
$$

这个函数的参数「**构建输入**」是指用于确定一个软件包的全部要素，也就是会影响构建的所有因素。具体来说，以下信息都属于输入：

- 依赖关系
- 源代码
- 构建脚本
- 环境变量
- 系统架构
- 等等……

这里我们再来想想隐式依赖。隐式依赖正是构建的副作用。大多数构建系统会把相当于构建输入的信息写在软件包定义文件里，但由于还会受到未在定义文件中明确记述的外部因素影响，因此带有副作用。

而在 Nix 中，只有被明确指定为构建输入的东西才会影响构建，外部因素完全无法干涉。因此 Nix 的构建具有引用透明性——对同样的「输入」，它总是返回同样的「构建产物」。

## 沙箱环境^[[Sandboxing - Zero to Nix](https://zero-to-nix.com/concepts/sandboxing)]

那么实际上是如何实现纯函数式构建的呢？答案是利用**沙箱**环境。

沙箱（直译：箱庭）指的是与宿主系统隔离并受到保护的环境。用过 VM 或 Docker 的人可能更容易想象。

Nix 只把被指定为**输入**的东西引入沙箱内，然后执行构建。

![沙箱环境的示意图。从宿主系统把 shell、环境变量、依赖包、源代码指定为输入，只有被指定为输入的东西被引入沙箱环境。沙箱内禁止访问宿主的软件包、宿主的环境变量以及互联网。在沙箱内执行构建后，构建产物被输出到宿主系统。](/images/nix-introduction/sandbox.png)
_沙箱示意图_

访问沙箱之外的行为被视为副作用而受到限制。

输入的指定必须做到严格。首先，连执行构建脚本所用的 shell 都必须指定。即便是在普通环境中几乎肯定已经安装的基础工具，也必须显式指定；例如想使用 `cp`、`ls`、`rm` 这些命令，就必须把 `coreutils` 指定为构建输入。万一构建输入里什么都没指定，那么沙箱内就真的什么都不存在。

### 禁止访问互联网

这可能让你有点吃惊：在 Nix 的沙箱环境中无法访问互联网。访问互联网当然是副作用，而且响应也无法保证是幂等的。

但是，现代编程语言的包管理器从互联网下载软件包早已是理所当然的事，一旦不能用互联网就非常不便。Nix 是怎么解决这个问题的呢？

Nix 的构建系统中有一个叫作 **Fetcher** 的「逃生口」式功能。它是一种在不损害可复现性的前提下从互联网获取资源的机制。Fetcher 要求在下载之前先指定待下载资源的哈希值。构建执行时，如果通过 Fetcher 获取到的资源算出的哈希与事先指定的哈希不一致，就会立即让构建失败。

Fetcher 不只有一个，而是按用途存在各种各样的 Fetcher，比如专门从 GitHub 下载源代码的 Fetcher。

## 可复现性得到保证了吗？

多亏了沙箱环境，我们已经保证了对同样的输入会输出同样的构建产物。但还残留着以下问题：

1. 如何指定输入
2. 如何解决运行时依赖

真要开始构建软件包时，如果输入本身会发生变化，那前面的一切就都白费了。要想有效利用沙箱式构建系统，就需要一套严格指定输入的机制。

另外，运行时依赖是构建系统无法解决的。特别是运行时依赖的典型代表——共享库，正是引发依赖地狱的主要原因。
